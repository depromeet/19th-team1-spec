# 19th-team1-spec

디프만 19기 1팀의 기획 정본 레포. **PRD는 이 레포가 정본**이고, 화면은 피그마, 코드는 클라이언트·서버 레포에 있다.
노션 기능명세서는 이 PRD의 기반 문서이고, 결정이 바뀌면 이 레포를 먼저 고친다.

## 구조

| 경로 | 내용 | 담당 |
|---|---|---|
| `prd/prd.md` | 제품 전체: 문제, 증명할 것, 여정, 범위, 지표, 용어 | 전체 |
| `prd/features/` | 기능별 요구사항 (파일 하나 = 기능 하나) | 파일마다 다름 (아래) |
| `prd/open-questions.md` | 아직 안 정해진 것 (OQ) | 전체 |
| `prd/decisions.md` | 날짜별 결정 기록과 출처 | 전체 |
| `design/` | 피그마 링크, 화면 ↔ ID 매핑, 문구, UT 계획 | 디자인 |
| `fe/` | 웹 구현 메모 (라우트, 화면별 상태) | 웹 |
| `be/` | 데이터 모델, 처리 흐름 (API는 Swagger 링크) | 서버 |

### 기능 파일과 담당 파트

| 파일 | ID | 기능 | 담당 |
|---|---|---|---|
| `collect.md` | C | 수집 | 서버 · 웹 |
| `organize.md` | O | 정리 | 서버 |
| `home.md` | H | 다시 발견 (인사이트 홈, 카테고리 탭) | 디자인 |
| `retrieve.md` | R | 꺼내 쓰기 (챗봇) | 디자인 · 서버 |
| `nudge.md` | N | 다시 부르기 (알림) | 디자인 |
| `trust.md` | P | 관리·신뢰 (로그인, 삭제, 개인정보) | 서버 · 디자인 |

담당 파트의 승인이 있어야 그 파일을 바꾸는 PR이 머지된다 (`.github/CODEOWNERS`).

## ID 규칙

- 요구사항: `기능 글자-두 자리` — 예) `R-02` 좁혀가기
- 사용자 여정 `UJ-n`, 성공 지표 `SM-n`, 열린 질문 `OQ-nn`, 결정 `D-MMDD-nn`
- **한 번 붙인 ID는 바꾸거나 재사용하지 않는다.** 빠지면 `상태: 삭제`로 남긴다.
- 피그마 프레임 이름, 코드 이슈·PR에도 같은 ID를 쓴다 — 예) 프레임 `R-02 좁혀가기`, 커밋 `feat(web): 좁혀가기 칩 (R-02)`

## 상태

| 상태 | 뜻 |
|---|---|
| 확정 | 회의에서 정했다. 출처 있음 |
| 논의 | 팀에서 나왔지만 안 정했다. 관련 OQ 있음 |
| 보류 | 이번 범위에서 뺐다. 이유 있음 |

## 읽는 순서

1. `prd/prd.md` — 10분이면 전체가 잡힌다
2. 내 파트 담당 기능 파일
3. `prd/open-questions.md` — 내 이름이 있는 줄

## 의견 주기

- **질문·피드백**: Issues → "기획 피드백" 폼. 대상 ID를 적는다
- **PR 리뷰**: 바뀐 줄에 바로 댓글. 동의하면 Approve

## 고치기

1. 브랜치 `docs/<영어-소문자-하이픈>` — 예) `docs/retrieve-empty-answer`
   - 웹에서 고칠 때: 파일 열기 → 연필 버튼 → 수정 → "Propose changes" 하면 브랜치와 PR이 자동으로 만들어진다
2. PR 템플릿의 "바뀌는 ID", "근거"를 채운다. 근거 없는 확정은 받지 않는다
3. 결정이 바뀌었으면 `prd/decisions.md`에 한 줄 추가
4. 담당 파트 승인 + 총 2명 승인 후 Squash 머지. 머지되면 디스코드로 알림이 간다

> GitHub가 어려운 사람은 이슈나 디스코드에 내용을 남기면 담당 파트가 대신 PR로 옮긴다.
